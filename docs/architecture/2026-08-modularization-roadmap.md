# 可转债量化看板模块化路线图

状态：已决策，按阶段迁移
日期：2026-08-18

## 结论

不整体重写，也不直接套用某个参考项目。采用“模块化单体 + 绞杀式迁移”：保持现有页面、HTTP 接口、MiniQMT 与交易保护链路可用，每次沿一条完整业务链抽出领域逻辑、应用编排和基础设施适配器，并用回归测试保护行为。

第一条纵切片已经落在 `src/`：通达信选股读取、代码标准化、名称目录、看板合并计划和本地 API 写入彼此分离。后续服务端、Python 和前端拆分复用同一模式。

真实运行链为：原生多页面前端 → Node 5173 → Python 18890 → Windows QMT Bridge 18888。问题不是“技术栈旧”，而是业务规则、I/O、路由和视图状态集中在少数文件中，导致修改范围难预测、单元测试只能通过源码片段抽取，数据来源也缺少统一契约。

Git 基线同样需要治理：当前开发分支相对 `origin/main` 已积累 41 个提交，并有一批未提交业务改动和运行产物。CI 只能检查已经提交并推送的代码，无法发现开发机上忘记提交的文件，因此必须同时建立本地完成定义、短分支和远端必需检查。

## 参考项目怎么选

参考项目按“可借鉴的层”筛选，不选一个项目替换全部：

| 参考 | 借鉴 | 不直接采用的原因 |
| --- | --- | --- |
| `course_ai_quant_system_w12` | 策略注册、策略生命周期、审批状态、路由分层、工作台产品主干 | Python/FastAPI 运行形态不同；自身也有平铺胶水和外部依赖，整体迁移会重做已稳定的前端和 QMT 网关 |
| `web3-quant-sandbox` | `src/` 分层、PIT 数据约束、防前视检查、WFO/PBO/DSR/CPCV、执行边界、统一 verify | 它是研究/教学沙箱，不负责当前看板的实时行情、板块编辑和受控交易体验 |
| EasyXT | QMT/通达信适配器、数据源接口和板块读取思路 | Windows 本地 `xtquant`/RPyC 与现有 HTTP QMT Bridge 协议不同 |
| ZVT | Schema、Provider、查询接口和领域对象思路 | 框架版本、存储模型和 Windows QMT 假设会引入新的迁移成本 |
| TradingAgents、Qbot、脚本集合 | 研究提案或策略素材 | 不作为状态账本、风控、数据底座或实时执行主干 |

选择规则：只有同时满足“解决当前明确问题、边界可独立迁移、能写契约测试、不改变交易安全边界”的设计才进入主项目。

## 目标架构

```text
src/
  domain/             纯业务规则：代码、板块、信号、订单约束
  application/        用例编排：导入选股、刷新行情、生成信号、回补
  infrastructure/     QMT/TQ/外部行情、SQLite/JSON、进程与时钟适配器
  interfaces/         HTTP 路由、CLI、浏览器页面入口

frontend/
  shared/             API 客户端、调度器、格式化、图表基础件
  board/              主看板页面模块
  bond/               单债页面模块
  trading/            交易页面模块

tests/
  unit/               纯规则和边界条件
  contract/           HTTP/数据契约与供应商样本
  integration/        本地 Node/Python 只读链路
```

不要求一次搬完，也不要求立刻引入 React/Vue、TypeScript、FastAPI 或新的数据库。目录边界和依赖方向先稳定，技术替换要有单独收益证明。

## 不可破坏的边界

- health 或 HTTP 200 不等于真实行情，验收继续检查代表代码、时间戳和覆盖数。
- 普通五档或快照推断不能改名为 Level-2 逐笔事实。
- 通达信/QMT/外部行情必须经适配器进入统一数据契约，禁止页面静默混源。
- 实盘入口的回环、同源、解锁、预览令牌、限额和写后审计不能在重构中弱化。
- 每一阶段都必须可单独回滚；不以“新架构已搭好”替代真实页面和 API 验收。
